## Architecture

### Overview
lcloud is a **modular monolith** written in Go. The backend exposes a REST API (Gin) consumed by a React SPA. Internal modules are cleanly separated with defined interfaces — auth, volume, monitoring, indexer, plugin, task — but run in a single process. The architecture is designed to be extractable into independent services later if needed, but that complexity is deliberately deferred.

### Domain Map

| Domain | Responsibility | Key Folder |
|---|---|---|
| Auth | User management, JWT auth, admin/user roles | `internal/auth/` |
| Volume | Volume CRUD, file ops, `.volume.json` source of truth, disk selection | `internal/volume/` |
| Monitoring | Space stats, file type breakdown, multi-disk aggregation | `internal/monitoring/` |
| Indexer | `VolumeIndexer` interface + Bleve implementation | `internal/indexer/` |
| Plugin | go-plugin runtime, event bus, plugin lifecycle | `internal/plugin/` |
| Task | gocron scheduler, macro executor, task CRUD | `internal/task/` |
| API | Gin routes and handlers (thin — call services only) | `internal/api/` |

### Volume structure on disk

Each volume is a self-describing directory. Structure created at volume creation:

```
./ (volume root — directory named after the volume UUID)
├── .volume.json              ← source of truth (portable — re-importable without DB)
│                               fields: id, name, owner_id, quota_bytes, filters
│                               (allowed/blocked extensions), encryption (stub),
│                               created_at, disk_path
├── userdata/                 ← user-accessible files
├── cache/
│   ├── index/                ← Bleve index files (metadata: name, path, MIME, size, dates, SHA256)
│   ├── thumbnails/           ← image/video thumbnails for the web UI
│   └── metadata/             ← file metadata cache (computed, can be rebuilt)
├── plugins/
│   └── <plugin-id>/          ← isolated per-plugin persistent data per volume
├── logs/                     ← planned structure; populated post-MVP
└── .trash/                   ← soft-deleted files (portable; see ADR-005)
    └── {file-id}/
        ├── {basename}        ← original file bytes
        └── meta.json         ← trash metadata (original_path, deleted_at, …)
```

**Portability rule:** lcloud can re-import any volume by pointing to its root directory and reading `.volume.json`. PostgreSQL is a performance cache, not the source of truth for volume config. Any write to volume config must update `.volume.json` first.

### VolumeIndexer interface

```go
type VolumeIndexer interface {
    Index(file FileMetadata) error
    Delete(path string) error
    Search(query SearchQuery) ([]FileMetadata, error)
    Rebuild(volumePath string) error
    Close() error
}
```

MVP implementation: `BleveIndexer` — indexes metadata only (name, relative path, MIME type, size, modification date, SHA256 hash).
Post-MVP: same interface, content extraction added (text files, PDFs, audio/video metadata, OCR) without changing callers.

### Plugin system

Plugins are external binaries communicating with lcloud via go-plugin (HashiCorp):
- lcloud → plugin: typed RPC calls (event dispatch, plugin API surface)
- Plugin → lcloud: event emission, volume primitive access via the plugin API
- Isolation: each plugin runs in its own subprocess; crash does not affect the core
- Data: each plugin has `./plugins/<plugin-id>/` in the volume for isolated persistent storage
- Discovery: lcloud scans the `plugins/` directory at startup and loads valid binaries

Plugin SDK: a minimal Go package providing the interface to implement + helper utilities.
Post-MVP: multi-runtime support (WASM as a second option alongside subprocess).

### Event bus

Core events emitted by lcloud:
- `file.uploaded`, `file.deleted`, `file.moved`, `file.renamed`
- `volume.created`, `volume.deleted`, `volume.updated`
- `task.executed`, `task.failed`
- `plugin.registered`, `plugin.unregistered`
- `volume.alert.usage` (emitted by the `alert_usage` macro)

Plugins subscribe to events by name. Plugins may emit custom events that other plugins can subscribe to.

### Data flow

```
Browser → React SPA → REST API (Gin) → Service layer → Domain modules → PostgreSQL / disk
                                     ↑ auth middleware (JWT validation)
Plugin binary ←→ go-plugin RPC ← Plugin runtime ← Event bus ← Domain modules
```

### Dependency rules

```
Types → Config → Repository → Service → API handler → HTTP
```

Each layer may only import from layers to its left.
Plugin runtime is a lateral module — it imports Service layer but is not imported by it.

### Key architectural decisions

| Decision | Rationale | Alternatives rejected |
|---|---|---|
| Modular monolith over microservices | Lower operational complexity for a solo self-hosted project; extractable later if needed | Microservices — disproportionate overhead for MVP |
| `.volume.json` as source of truth | Volumes are portable and re-importable without the database | DB-only — would break portability |
| go-plugin (subprocess) for plugins | Battle-tested (HashiCorp/Terraform), language-agnostic, good isolation | WASM — ecosystem too young; native .so — Linux-only, no isolation |
| Bleve for indexing | Go-native, embedded, stores in volume directory, same interface supports content search later | SQLite FTS5 — would require migration when content search is needed |
| Docker Compose for deployment | Standard for self-hosted tools, single command, well understood by the target audience | Kubernetes — disproportionate complexity for MVP (deferred to IDEAS.md) |

> Significant architectural changes after project start must be captured as ADRs in `docs/adr/` via the `documentation-and-adrs` skill.

### Anti-patterns
- No direct disk writes outside `internal/volume/`
- No business logic in Gin route handlers — they call services, nothing else
- No direct database calls from the plugin runtime — plugins access data only via the plugin API
- No duplication of Tech Stack or Project Structure content into SPEC.md — reference this file
- No change to the volume directory structure or `.volume.json` schema without an ADR

## Deployment workflow

> This is the immutable deployment workflow for this project.
> Any deviation must be discussed and documented as an ADR.

### Setup
- **Repository:** GitHub — public (open-source)
- **Platform:** Docker Compose (self-hosted)

### Strategy

`main` is the stable and deployable branch. Day-to-day work happens on short-lived branches merged into `main` via PR.

**Branch flow:**
- `main` → stable, deployable at any time
- `feature/*` → new user-facing feature or project phase
- `fix/*` → bug fix
- `docs/*` → documentation-only change
- `chore/*` → maintenance/config change
- `refactor/*` → behavior-preserving code simplification

All task branches are merged into `main` via PR after review and checks.

**Environment variables:**
- Managed in `.env` file on the server (never committed)
- `.env.example` in repo lists all required variables (empty values)

**Database migrations:**
- GORM AutoMigrate for development
- Manual SQL migrations for production deployments (tracked in `docs/adr/`)

**Rollback:**
- `git revert <commit>` + push to `main`
- Redeploy with `docker compose up -d --build`

**URLs:**

| Environment | URL |
|---|---|
| Local | `http://localhost:8080` |
| Production | configured per self-hosted deployment |

**Never:**
- Commit or push directly to `main` unless explicitly requested
- Merge a task branch without review/checks
- `git push origin main --force`
- Commit real `.env` files

## Constraints

### Security level
- [x] Production — user data, JWT auth, HTTPS expected in front of the Docker service (reverse proxy responsibility of the deployer)

### Data classification

| Data type | Sensitivity | Rule |
|---|---|---|
| User credentials | PII | Bcrypt hashed passwords; JWT tokens expire |
| Volume file contents | User data | Stored on user's own hardware; encryption opt-in (post-MVP) |
| Volume metadata | User data | Stored in `.volume.json` inside the volume — never leaves user's infrastructure |

### Compliance
- GDPR: Does not apply (self-hosted — user is the data controller)
- Data retention: User-controlled (no third-party storage)

### Coverage targets
- Critical paths (auth, file upload/download, volume CRUD): 80% minimum
- Global: best-effort for MVP
